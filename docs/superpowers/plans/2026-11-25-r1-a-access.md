# R1-A Access Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Village runs its admin with more than one person safely. Administrators create Users, hand them Access Links, give each a Role built from the fixed Permission catalogue, deactivate people who leave, and read the Audit Log. Sensitive actions need a fresh re-authentication (Sudo Mode), failed sign-ins are throttled, and a registered Passkey is a second way in.

**Architecture:** Authorization lives in a new `access` module of the `pranata` crate. The session lookup that already runs on every request also loads the User's Role and Permissions, so handlers check them with one call and a changed Role applies on the next request. Users, Roles and the Audit Log get admin endpoints under `/api/admin/*` and matching admin screens in `apps/web`. Sudo Mode is a timestamp on the session. Throttling counts failures per account in PostgreSQL and limits requests per client IP in memory (tower_governor). Passkeys use webauthn-rs with ceremony state kept in PostgreSQL.

**Tech Stack:** As R0 (spec section 8), plus webauthn-rs 0.6.2 (features `danger-allow-state-serialisation`, `conditional-ui`), webauthn-authenticator-rs 0.6.2 (dev only, feature `softpasskey`), tower_governor 0.8.0, `@simplewebauthn/browser` 14.0.0. Versions checked on crates.io and npm on 2026-11-25. Re-check each one when you add it, and use the latest stable.

**Spec:** `docs/superpowers/specs/2026-11-24-pranata-r1-cms-design.md` (D-21, D-30–D-35, D-38, D-39). Also read `CONTEXT.md` (Access section), `docs/adr/0007-access-links-instead-of-email.md`, `docs/adr/0008-ui-components-enforced.md`, and the R0 plan's "Carry-over to the Access plan (R1-A)" section, which this plan picks up in full (see the table at the end).

## Global Constraints

- Every R0 global constraint still holds: atomic Conventional Commits with a DCO sign-off (`git commit -s`) and the session's trailers, allowed scopes `api, web, infra, ci, tools, deps, adr, spec, plan, release`, `**Decisions:**` on every task, no `.prototype/` commits, no village data in code (D-02), `unsafe_code = "forbid"`, clippy pedantic as errors, SQLx compile-time macros with committed `.sqlx/` (D-39), no raw form controls in feature code (D-38).
- One task is one PR, branched from `main`. Keep each PR small. GitHub refused to rebase-merge a ~150-commit PR in R0.
- Migrations: the file names below give the order and the purpose. Number each one with the next free number when you write it (`0008_…`, `0009_…`), because tasks may merge in a different order.
- Rollback (D-50): `just deploy` rolls back to the previous image version without rolling back the schema, so release N-1 must keep working on the new schema. A new column is nullable or has a default that N-1's inserts can live with. The one accepted exception is Task 3's NOT NULL `users.role_id`: on N-1 (0.1.0) it breaks only `pranata user create-admin`, which runs at install time, not in normal use. The R0 plan's carry-over to R1-E records it for the N/N-1 test.
- Every new problem `code` and field error `code` the API can return needs Indonesian copy in `apps/web/src/lib/errors.ts`. `apps/web/src/lib/errors.test.ts` scans `apps/api/src` and fails otherwise. The copy for each new code is given in the task that introduces it.
- Every endpoint a task adds names its `operation_id` in parentheses after the path, for example `POST /api/auth/sudo` (`confirmSudo`). Use exactly that name in `#[utoipa::path(operation_id = …)]`. Orval derives the web hook names from it (`confirmSudo` → `useConfirmSudo`), and later tasks use those hooks.
- After any API contract change, run `just gen` and commit `apps/api/openapi.json` and `apps/web/src/api/generated` in the same commit as the API change (`just check-contract` gates this).
- D-35: every endpoint that changes data writes an Audit Entry in the same transaction. Each task's tests assert the entry.
- D-21: Users are never deleted. Passkeys, sessions, Access Links and unused Roles are not on D-21's list. A Passkey and an unused Role may be deleted. Sessions are deleted at sign-out. Access Links are kept as records.
- Permission strings are exactly `village.manage`, `content.write`, `content.publish`, `budget.manage`, `audit.read`, `user.manage`, `role.manage` (D-33). Nothing else, and no village-defined Permissions.
- The Sudo Mode window is 10 minutes (D-31): `SUDO_WINDOW = Duration::minutes(10)`.
- Check order in every admin handler: session (401 `unauthenticated`) → Permission (403 `permission_denied`) → Sudo Mode (403 `sudo_required`) → escalation rules (403) → request validation (422) → domain rules (404, 409). A User without the Permission therefore never learns whether a request would have needed Sudo Mode or was valid. Tests that assert one of these codes set up everything earlier in the chain to pass.
- No escalation (D-33). These rules hold in every task:
  - Only an Administrator may assign or remove the Administrator Role.
  - Only an Administrator may edit, deactivate or reactivate an Administrator, issue them an Access Link, or remove their Passkeys.
  - Nobody changes their own Role, and a non-Administrator cannot create, edit or delete the Role they hold.
  - A non-Administrator can only put Permissions they hold into a Role, and can only assign a Role whose Permissions they all hold.
  - Breaking a rule gives 403 with code `administrator_only`, `own_role` or `permission_not_held`. Copy:
    - `administrator_only` → "Hanya Administrator yang dapat melakukan ini."
    - `own_role` → "Anda tidak dapat mengubah peran Anda sendiri."
    - `permission_not_held` → "Anda hanya dapat memberikan hak akses yang Anda miliki."
- Admin UI copy is Indonesian and follows `.prototype/admin/index.html` (screens `pengguna`, `peran`, `log-audit`). The prototype is a local visual reference only.

## Review Focus

1. **Two Administrators demote or deactivate each other at the same moment**, leaving no active Administrator → exactly one request succeeds and the other answers 409 `last_administrator`. Test `concurrent_demotions_keep_one_administrator` in Task 7.
2. **The Sudo Mode window runs out while the confirm dialog is open, or between confirming and saving** → the API answers 403 `sudo_required`, the web app asks again and retries the original request once, and it never loops. Tests `sudo_expires_exactly_at_ten_minutes` (Task 4) and `retries the request once after confirming` (Task 9).
3. **Someone floods failed sign-ins for the Administrator's username**, so password sign-in is throttled → the real Administrator can still sign in with a Passkey. Test `passkey_sign_in_ignores_password_throttle` in Task 13.
4. **A Role's Permissions change while its Users are signed in** → the change applies on their next request, with no sign-out. Test `role_change_applies_to_signed_in_users` in Task 8.
5. **An Access Link went to the wrong WhatsApp chat, so the Administrator issues a second one** → the first link answers 410 and only the newest works. Test `issuing_a_link_revokes_earlier_unused_links` in Task 7.

### Task 5: Login throttling per account and per IP

**Decisions:** D-34, D-39

**Files:** Create `apps/api/src/auth/throttle.rs`, `src/http/client_ip.rs`, `migrations/NNNN_login_failures.sql`, `tests/throttle.rs`. Modify `src/http/auth.rs`, `src/http/mod.rs`, `src/http/request_id.rs` (log the client IP), `src/auth/access_link.rs` (clear the counter on redeem), `src/main.rs`, `Cargo.toml`, `infra/README.md`.

**Interfaces:**
- Migration: `login_failures(id bigint generated always as identity primary key, username text not null check (char_length(username) <= 64), at timestamptz not null)` with an index on `(username, at)`. The app role gets `SELECT, INSERT, DELETE`, and the migration states `REVOKE UPDATE, TRUNCATE ON login_failures FROM pranata_app`, because migration 0001's default privileges grant UPDATE on every new table.
- Per account (`src/auth/throttle.rs`):
  - `pub const ACCOUNT_WINDOW: Duration = Duration::minutes(15)` and `pub const ACCOUNT_LIMIT: i64 = 10`.
  - `pub async fn check(db: &PgPool, username: &str, now: OffsetDateTime) -> Result<(), ApiError>` counts the failures for the lower-cased username within `ACCOUNT_WINDOW`. At `ACCOUNT_LIMIT` or more it answers 429 `too_many_attempts` with `Retry-After` set to the seconds until the oldest counted failure leaves the window. It runs before argon2, so a throttled attempt is cheap.
  - `pub async fn record_failure(db: &PgPool, username: &str, now: OffsetDateTime) -> anyhow::Result<()>` runs outside any request transaction, so a rollback cannot lose it. ## Calls made in this plan

The spec leaves these open. They are this plan's proposals; correct them before execution if they are wrong.

- Throttling numbers: per account, 10 failures in 15 minutes lock password sign-in for the rest of the window. Per IP, a burst of 20 unauthenticated auth requests, refilling one every 3 seconds.
- Accepted risk: the account counter is keyed on the username, so anyone who knows an Administrator's username can keep their password sign-in locked with one failed attempt every 90 seconds. Keying on username and IP together would let a distributed attack through, and D-34 asks for per-account limits. Recovery: Passkey sign-in ignores the counter, redeeming an Access Link clears it, and `just create-admin` makes a new Administrator on the server. Task 5 documents this in `infra/README.md`.
- The per-IP burst is not configurable. The e2e tests stay within it (Task 5 records the headroom), and a knob would be one more setting that operators could get wrong.
- Passkey sign-in is username-less (discoverable credentials) and is not blocked by the per-account password counter. Otherwise an attacker could lock the Administrator out.
- Signing in opens the Sudo window, so a fresh sign-in does not ask for the password again within 10 minutes.
- Roles may be deleted while no User, active or deactivated, holds them. D-21 does not list Roles.
- Deactivated Users can be reactivated. Their username stays reserved either way.
- An Administrator cannot deactivate themselves (409 `cannot_deactivate_self`), on top of the last-Administrator rule.
- Linking a User to an Official (the prototype's "Perangkat desa" column) waits for Plan R1-B (recorded in the R0 plan's carry-over to R1-B).
- The sign-in carousel shows built-in product slides until Plan R1-C can use photos from published Albums (recorded in the R0 plan's carry-over to R1-C).
- Requiring Sudo Mode to delete published content (D-31) is built with the content in Plan R1-C (recorded in the R0 plan's carry-over to R1-C).
- Caddy moves to host networking so it sees client addresses (Task 6). This is the one change in this plan that touches the deployment shape, so Task 6 records it in ADR 0009, and the R0 plan's carry-over to R1-E asks R1-E to cover it in the install guide and the stranger install test.
